# TeslaSync PWA & device layer

Everything that makes TeslaSync behave like an installed application rather
than a tab lives here or is wired from here. This document is the map.

| Concern | Owner |
| --- | --- |
| Installability (manifest, icons, iOS/Android) | `web/vite.config.ts` (`VitePWA.manifest`), `web/index.html`, `hooks/usePwaInstall.ts`, `components/feedback/InstallPrompt.tsx` |
| Offline caching + disclosure | `sw/apiCachePolicy.ts`, `sw/sw.ts`, `hooks/useServiceWorkerBridge.ts`, `components/feedback/CachedDataNotice.tsx` |
| Offline announcement (global, singular) | `components/feedback/OfflineBanner.tsx`, mounted once by `components/feedback/ReloadPrompt.tsx` |
| Identity-transition purge | `sw/purgeApiCache.ts`, `lib/resilience.ts` (`navigateToReauth`), `components/feedback/ReloadPrompt.tsx` (`auth.logout`) |
| Update lifecycle | `hooks/usePwaUpdate.ts`, `components/feedback/UpdatePrompt.tsx`, `sw/buildContract.ts` |
| Notification policy + deep links | `sw/notificationPolicy.ts`, `sw/deepLink.ts`, `hooks/useDeviceNotificationPrefs.ts`, `features/notifications/components/DeviceNotificationPrefsPanel.tsx` |
| Low-bandwidth mode | `hooks/useLowBandwidthMode.ts` (+ consumers) |
| Background/foreground recovery | `hooks/useAppLifecycle.ts` |
| Executable contract | `web/scripts/check-pwa-contract.mjs` (runs on `postbuild`) |

Every module under `src/sw/` except `sw.ts` is **pure** — no `self`, no DOM,
no Cache Storage — because the page imports the same files. `sw.ts` is
excluded from the app TypeScript project (`tsconfig.json`) and checked
separately by `tsconfig.sw.json` with the WebWorker lib
(`npm run typecheck:sw`).

## PWA-01 — Installability

**Android / Chromium.** The manifest is generated by vite-plugin-pwa from
`vite.config.ts`. It declares `id`, `scope`, `start_url`, `display`,
`display_override`, `launch_handler`, four icons (192/512 in both `any` and
`maskable`) and three shortcuts. `check-pwa-contract.mjs` verifies that every
declared icon exists in `dist/`, that its PNG IHDR dimensions match the
declared `sizes`, that `start_url` is inside `scope`, and that each shortcut
URL exists in `lib/routeRegistry.ts`.

**iOS / Safari.** WebKit ignores the web manifest's `display` and keys
standalone launch off `<meta name="apple-mobile-web-app-capable">`. Both that
tag and the standardised `mobile-web-app-capable` are present in
`index.html`, alongside `apple-mobile-web-app-title`,
`apple-mobile-web-app-status-bar-style=black-translucent`, and
`apple-touch-icon`. The contract script asserts all of them.

**Safe areas.** `index.html` sets `viewport-fit=cover`; the
`safe-top`/`safe-bottom`/`pb-safe`/`safe-left`/`safe-right` utilities in
`index.css` map to `env(safe-area-inset-*)`. Every fixed-position PWA surface
(`InstallPrompt`, `UpdatePrompt`, the offline disclosure) offsets itself with
`env(safe-area-inset-*)` so nothing sits under the notch or the home
indicator.

**Honesty about iOS.** `beforeinstallprompt` does not exist in WebKit and
Apple has declined to ship it. `detectInstallCapability()` therefore returns:

- `native-prompt` only when a real `beforeinstallprompt` was captured,
- `ios-manual` on iOS **Safari** → the banner renders the literal
  Share → Add to Home Screen → Add steps and **no Install button**,
- `ios-unsupported-browser` in Chrome/Firefox/Edge on iOS and in in-app
  webviews, where installation is impossible → the banner renders nothing,
- `installed` when already running standalone.

### Manual checks that remain

Automated checks cannot open a real phone. Still to verify on device:

- Android Chrome: long-press the installed icon and confirm the three
  shortcuts appear and launch the right route.
- Android: confirm the maskable icon is not clipped on a circular/squircle
  launcher.
- iOS Safari 17+: Add to Home Screen, then confirm the app opens without
  Safari chrome, that the status bar is translucent over the dark background,
  and that the home-screen label reads "TeslaSync".
- iOS: confirm no white bar under the home indicator on an iPhone with a
  notch/Dynamic Island.
- **Splash screens on iOS** are generated from `background_color` +
  `apple-touch-icon` on iOS 15+. Bespoke `apple-touch-startup-image` assets
  (one PNG per device resolution) are **not** shipped — adding them requires
  generating ~15 images and is tracked as future work.
- **Manifest `screenshots`** are not shipped, so Android shows the compact
  install dialog rather than the rich one. Also future work (needs real
  captured screenshots).

## PWA-02 — What may be cached, and disclosing it

`sw/apiCachePolicy.ts` holds a hand-vetted **allowlist** of authenticated
read-only endpoints. Everything else — every mutation, every settings/admin/
auth/export/share path, and every endpoint nobody has explicitly reviewed —
is never intercepted and therefore never stored.

Two independent gates:

1. `classifyApiRequest()` — GET only, same-origin, under `/api/v1`, not
   matching `SENSITIVE_PATH_MARKERS`, and matching an exact allowlist pattern.
2. `isCacheableApiResponse()` — status 200, **not** `redirected` (a ForwardAuth
   302 to the login page must never be pinned under an API URL), not opaque,
   no `Set-Cookie`, and not `Cache-Control: no-store|private`.

Cached entries are stamped with `x-teslasync-cached-at`; entries served from
cache also carry `x-teslasync-cache-source: cache`. `CachedDataNotice`
consumes that via `useServiceWorkerCacheStatus()` and renders *"You're
offline. Showing data cached 12 minutes ago (26 Aug 2026, 14:02)"* — never an
unqualified value. When the response becomes uncacheable, the previously
stored copy is evicted rather than left to outlive its validity.

**Max-age is enforced on the fallback, not just recorded.** The offline branch
reads the stamp with `readCachedAt()` and refuses anything older than
`API_CACHE_MAX_AGE_SECONDS` (12 h) via `isCachedEntryExpired()`. An expired
entry — and any entry whose stamp is missing or unparseable, which counts as
unknown and therefore expired — is deleted and the original network failure is
re-thrown, so the UI shows its offline/error state instead of a confidently
wrong half-day-old battery percentage.

**Blanket disclosure quotes the OLDEST capture time.** A page renders several
cached reads at once. `useServiceWorkerCacheStatus()` exposes
`oldestCachedAt`, `newestCachedAt` and `timestampedCount`; the root notice
leads with the oldest (the staleness ceiling of what is on screen) and adds
"captured between X and Y" when the spread is real. Quoting only the newest
would understate the age of every other panel. A caller that knows its own
timestamp passes `cachedAt` and gets a per-view disclosure instead.

**Identity transitions purge.** `sw/purgeApiCache.ts` is the sender, kept in
this leaf module so `lib/resilience.ts` can call it without closing an import
cycle through `useVersionWatcher` → `api/client` → `resilience`. Both funnels
are wired and both are covered by `check-pwa-contract.mjs`:

- **Direct** — `navigateToReauth()` (the single funnel for sign-out, session
  expiry and reauth) purges and broadcasts `auth.logout` *before* it
  navigates.
- **Broadcast** — `ReloadPrompt` subscribes to `auth.logout` so a sibling tab
  that did not navigate purges too.

The purge runs two mechanisms: a synchronous `postMessage` to the controlling
worker (which outlives the document, so it completes across the navigation)
and a direct `caches.delete()` sweep that covers an uncontrolled page and, via
`isApiReadCacheName()`, every *previous build's* API bucket as well.

## PWA-03 / PWA-04 — Update lifecycle and contract safety

`registerType` is **`prompt`**, not `autoUpdate`, and `sw.ts` has **no
`install` listener**: a new worker waits until a page sends `SKIP_WAITING`.
`check-pwa-contract.mjs` fails the build if either of those regresses.

`usePwaUpdate()` owns the sequence:

- **Detect** — `useRegisterSW` + a 5-minute `registration.update()` poll +
  an extra check on foregrounding after ≥60 s hidden (mobile browsers freeze
  timers in background tabs).
- **Explain** — the banner shows the running build id and the backend's
  reported `app_version`.
- **Handshake** — `evaluateContractHandshake()` compares this build's version
  against the live backend's. Patch drift is ignored (rolling deploys); a
  major/minor gap in the server's favour means the assets in this tab predate
  the current API contract → `updateRequired`, the "Later" button disappears,
  and the service worker is told to purge every cached API read captured
  against the old contract.
- **Guard** — applying routes through `NavigationGuardProvider.confirmIfDirty()`,
  the same dialog that protects in-app navigation. Unsaved work blocks the
  reload and the banner explains why.
- **Defer** — "Later" snoozes for 30 minutes by setting `snoozedUntil` and
  **nothing else**. It must not call `setNeedRefresh(false)`: that flag is
  vite-plugin-pwa's record of "a worker is installed and waiting" and is only
  set again when a *different* worker installs, so clearing it made "Later"
  mean "never" for the worker already waiting. Visibility is
  `updateReady && (updateRequired || snoozedUntil == null)`. A required update
  cannot be snoozed at all.
- **Coordinate** — a dedicated `BroadcastChannel('teslasync:pwa-update')`
  tells sibling tabs an update is being applied. Clean tabs reload; a tab with
  unsaved work keeps its banner instead of losing the user's work.

**Announcement policy.** `role="alert"` carries an implicit
`aria-live="assertive"`, so the banner never pairs it with `polite`. A
*required* update is `role="alert"` + `aria-live="assertive"` (the tab is
running assets that no longer match the live API); an *optional* one is
`role="status"` + `aria-live="polite"`.

**Offline announcement ownership is global and singular.** `<OfflineBanner>`
is mounted once by `<ReloadPrompt>` — the app-root PWA host `main.tsx` renders
for every route and every presentation mode — and **not** by `<Layout>`. It
used to be a Layout-only mount gated on `presentation.mode === 'standard'`,
which made ownership positional: the six routes that never mount `<Layout>`
(`/quick-stats`, `/glance`, `/year-review/:year`, `/s/:token`, `/watch`,
`/onboarding`) and every report/kiosk view announced the transition **zero
times**.

Only the *visual* treatment is presentation-aware now; the announcement is
unconditional:

| Presentation mode | Rendering | Announced |
| --- | --- | --- |
| `standard` | the same fixed bottom-right `AlertBanner` as before | once, politely |
| `report` / `kiosk` | visually-hidden live region (no print/projection chrome) | once, politely |

The banner reads the mode from the module-level `getPresentationMode()` /
`subscribePresentationMode()` pair rather than the Router-bound
`usePresentationMode()` hook, so it works above the route tree and cannot
crash the shell. `<CachedDataNotice>` beside it stays a non-live `role="note"`
so the same transition is never spoken twice. `check-pwa-contract.mjs` fails
the build if `Layout.tsx` re-adds a mount or if the disclosure stops passing
`announce={false}`.

**Cache versioning.** Every contract-bearing Cache Storage bucket is named
`teslasync-<bucket>-<BUILD_ID>`; `activate` deletes every TeslaSync-owned
cache the current build does not claim. A previous build's JavaScript, CSS,
locale bundle or cached API read therefore cannot be paired with a newer API.
Vendor buckets (fonts, map tiles) are namespaced but not versioned, so they
survive deploys.

**ForwardAuth is preserved.** `index.html` is still excluded from the
precache; navigations use `NetworkFirst`, so a proxy 302 is observed as a real
response and `lib/resilience.ts` auth recovery still fires.

## PWA-05 — Notification preferences

Three layers, and they are not interchangeable:

| Layer | Scope | Route / hook |
| --- | --- | --- |
| Channel event-type routing | install-wide | `GET|PUT /api/v1/notifications/{channelID}/preferences` → `useNotificationPreferences`, `useUpdateNotificationPreference` |
| Quiet hours + severity bypass | install-wide | `/api/v1/notifications/quiet-hours` → `useQuietHours`, `useSaveQuietHours` |
| Device rules | this browser | `hooks/useDeviceNotificationPrefs.ts` → pushed into the SW |

The device layer exists because the API has no concept of a device: a phone,
a tablet and a desktop that all subscribed to Web Push share one server-side
configuration, so "critical only on my phone" cannot be expressed
server-side. It supports a master switch, per-category mutes, a severity
floor, per-vehicle scope, and a device-local quiet-hours window.

Evaluation order (pinned by tests): master switch → category → severity →
vehicle scope → quiet hours. Quiet hours **silences** (`silent: true`) rather
than suppressing, so nothing is lost and the Chromium silent-push budget is
not burned; only explicit mutes suppress. A payload with no resolvable vehicle
is treated as fleet-wide and is never filtered by vehicle scope.

**Test delivery** goes through the real service worker
(`registration.showNotification`) after running the real policy, and reports
the exact rule that suppressed it when it did — a silent no-op is
indistinguishable from a broken subscription.

### Backend gaps (not implemented here)

- There is **no `POST /api/v1/push/test`** route, so an end-to-end push
  round-trip (server → push service → device) cannot be triggered from the UI.
  The device test exercises permission + registration + policy + OS rendering
  only.
- `notification_preferences` has no per-device or per-vehicle dimension, and
  the push payload carries no `category`/`vehicle_id` field (the SW infers
  both from the `tag` prefix and the drill-through URL). Adding
  `category` and `vehicle_id` to `internal/webpush.Payload` would let the
  server filter before spending a push message.

## PWA-06 — Deep-link sanitisation

`data.url` in a push payload is attacker-reachable input that ends up in
`WindowClient.navigate()`. `sanitizeNotificationUrl()` is allowlist-only:

- resolve against our own origin, require the result to stay there;
- require `http:`/`https:` (rejects `javascript:`, `data:`, `blob:`, `file:`);
- reject protocol-relative (`//evil`) and backslash-smuggled origins;
- match the pathname against exact route shapes (vehicle, drive, charge,
  alert, notification inbox, data-repair case) with `:id` restricted to a
  positive integer;
- keep only `vehicle_id`, `alert`, `event`, `case`, `session`, `t`, `signal`,
  each re-validated; drop `redirect`/`next`/`return_to`/`url` and the fragment.

Anything that fails lands on `/notifications/inbox`. The URL is re-sanitised
in `notificationclick` because a notification can outlive a worker update.

> Note: `/data-repair?case=<id>` is allowlisted for forward compatibility, but
> `RepairCaseWorkspace` does not read the `case` query parameter yet, so the
> link currently opens the case list rather than the specific case.

## PWA-07 — Low-bandwidth mode

`hooks/useLowBandwidthMode.ts` is the single source of truth. It combines a
persisted tri-state preference (`auto` / `on` / `off`, in `localStorage`,
mirrored across tabs over a dedicated `BroadcastChannel`) with the network's
own signal (`navigator.connection.saveData` or a 2G-class `effectiveType`).
An explicit `off` beats the browser heuristic.

`resolveDataSaverPolicy()` turns that boolean into concrete knobs, and the
existing policies consume it:

| Surface | Consumer |
| --- | --- |
| Polling | `hooks/useRefreshPolicy.ts` — `useSaveData()` now ORs in the preference; `standard` pollers slow 4×, `background` pollers stop |
| Animations | `hooks/useMotionPreference.ts` — `reduce` becomes true, which every framer-motion component already honours |
| Charts | `components/charts/useChartPointBudget.ts` clamps the requested budget; `SmallMultiplesChart` uses it |
| Maps | `components/maps/MapTileLayer.tsx` falls back to the light raster basemap and sets `updateWhenIdle` |
| Service worker | images and map tiles are still **served** from cache but no longer **written** to it |

The control lives in `components/feedback/LowBandwidthControl.tsx` (reusable)
and is surfaced on the Browser notifications page via `DeviceDataUsagePanel`.

## PWA-08 — Background / foreground / suspension recovery

`hooks/useAppLifecycle.ts` listens to `visibilitychange`, `freeze`/`resume`
(Page Lifecycle API), `pageshow`/`pagehide` and `online`/`offline`, and feeds
the observable facts into the pure `deriveResumeAction()`:

- offline → do nothing (the `online` event handles it later);
- bfcache restore → always full recovery, however brief, because nothing
  remounted and every value on screen predates the restore;
- < 30 s away → nothing (`refetchOnWindowFocus` covers it);
- ≥ 30 s away → invalidate **active** queries only, plus reset the SSE pipe
  when it is disconnected or has been silent for > 60 s (mobile OSes tear the
  socket down without updating `readyState`), plus an out-of-band
  service-worker update check.
