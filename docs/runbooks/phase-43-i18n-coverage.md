## Summary

After Phase 42 (Tesla Fleet Telemetry Pipeline rewrite) + the Phase 43 domain ports
(prompts 0020 – 0038), every `t('…', …)` reference in `web/src/` must resolve to
a key defined in `web/src/i18n/en.json`. Domain ports added new SI labels
(distance/speed/temperature/pressure suffixes such as `{{unit}}/drive avg`,
`Distance (mi)`, `Battery Capacity (kWh)`, etc.) — many were registered in the
TSX call sites but never persisted to the bundle.

This prompt **audits and additively reconciles** the bundle. Per the
[Honesty Covenant rule 11](../../.github/prompts/db-refactor/0000-prompt-rules.md)
and ADR-005 #1, **no key was deleted** even when it appeared unused. Orphans
are reported here for future-prompt awareness, never pruned.

## Missing keys (deferred — parent-leaf collision)

108 keys remain missing per the line-by-line validator. **All 108 are
parent-leaf collisions**: the requested dotted key requires its parent
path to be an object, but the parent is currently a string leaf. Adding
them would require either:

1. Converting an existing string leaf into an object with the original
   value moved to a sub-key (e.g. `.label`) — **forbidden** because the
   original dotted key would no longer resolve, which is effectively a
   key deletion (see ADR-005 #1).
2. Renaming the call site in TSX (e.g. `comparison.monthlyDistance.aria`
   → `comparison.monthlyDistanceAria`) — **out of scope** for this
   prompt (allowed-files = `web/src/i18n/en.json`,
   `docs/runbooks/phase-43-i18n-coverage.md`, the log).

i18next handles all 108 gracefully at runtime via the positional
fallback / `defaultValue` argument supplied at every call site, so user-
visible English text continues to render correctly. A future cleanup
prompt with a wider allowed-files scope (TSX changes or coordinated
restructuring of the bundle plus its consumers) can resolve them — but
that is a deliberate decision that requires the never-delete invariant
to be re-evaluated in a follow-up ADR.

## Orphan keys (preserved)

992 leaves in `web/src/i18n/en.json` are not referenced by any line-by-line
`t()` call. Per ADR-005 #1 / rule 11, **none were deleted**. Many fall
into known-safe categories:

- **Multi-line `t()` references** the line-by-line scanner cannot see
  (e.g. options-object form spread across newlines). Cross-checked via a
  whole-file regex scan that found 151 of the 992 to be live references —
  these would otherwise be deleted by an aggressive cleanup pass and
  break translations at runtime.
- **i18next "key as value" labels** like `Run`, `Edit`, `Empty`, `Error`,
  `Test` that are referenced in components imported only by code not yet
  exercised by the static scan (e.g. command palettes, dynamic dashboard
  widgets registered at runtime).
- **Forward-compat keys for upcoming features** seeded by prior prompts
  but not yet wired in code — they protect translators who have already
  translated the strings into other locales.
- **Genuinely dead** post-Phase-42 keys (e.g. references to features
  removed by phase-42 prompt 0077). These are kept as historical
  artifacts; resurrection is one rename away.

## Methodology

1. Read the validator's baseline (`npm run i18n:validate -- --report=json`).
2. Apply automatic extraction (`npm run i18n:extract`) which adds 338 keys
   whose call sites supply a positional or `defaultValue` fallback string.
3. Manually author the 8 keys whose call sites use ternary, runtime,
   multi-line, or empty-string fallbacks (extractor cannot infer them).
4. Re-run the validator. Confirm `definedKeys` increased by exactly 346
   and `unused` is unchanged at 992 (no key was inadvertently dropped).
5. Diff the working copy against `HEAD:web/src/i18n/en.json` via
   `git show` + flat-key set difference; assert removed-set is empty.
